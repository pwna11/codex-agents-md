# Codex 防过度设计指南与 `AGENTS.md` 实战模板

> **摘要（Description）**：用 Codex + GPT-6 Astra 写代码，最头疼的往往不是代码质量差，而是“想太多、做太多”——改个版本号顺手给你搭一套测试框架，任务越滚越大，Token 飞速见底。本文基于过去一个月十多个真实踩坑会话的复盘，拆解 Codex 过度设计的根因，并提供一份可直接放进 `~/.codex/AGENTS.md` 的全局防过度设计配置与单次任务 Prompt 模板。

---

这两个月，我把主力开发任务都迁到了 Codex 上，搭配 GPT-6 Astra 使用。

用下来整体体感跟 Opus 还是有不少差距。最让人头疼的倒不是它性能不行、代码写得差，而是它**太爱“给自己加戏”了**——经常出现严重的过度设计（Over-engineering）。

OpenAI 在介绍 Astra 时，专门强调它擅长“守住任务边界”。但从我的实际使用体验和历史会话记录来看，情况恰恰相反：

你给它交办一个很小需求，它交回来的往往是一整套大幅超纲的改动。结果就是，你不仅要花不少精力去清理它多写的代码，Token 额度也跟着白白烧掉。

为了彻底治一下这个毛病，这几天我让 Codex 把过去一个月的会话历史完整翻了一遍，光典型的过度设计场景就揪出来十多个。结合这些踩坑记录，我把教训沉淀到了全局配置 `~/.codex/AGENTS.md` 里，并整理了一套**开箱即用的防过度设计模板**放在文末，推荐用 Codex 的朋友直接抄作业。

> 💡 **想直接复制模板？** 可以直接跳到文末查看 [7. 全局 `AGENTS.md` 与任务提示词模板](#7-全局-agentsmd-与任务提示词模板)。

## 1. Codex 的过度设计，大多是把“小任务”做成了“一套机制”

复盘十多个案例后我发现，Codex 很少漫无目的地乱改业务代码，它最典型的毛病是**把一次性的简单任务，顺手升级成一套工程机制**。

举个实际遇到的例子：
我让它更新基础镜像里的几个工具版本号。正常来说，改几个版本号数字，再跑个基本验证就够了。结果 Codex 不仅改好了版本，还顺手给我搭了一整套前端开发验证框架。

我只好停下来跟它解释：这个项目根本不需要开发前端，只是引用的开源组件自带了 Web 界面，开个浏览器确认页面能打开就行了。

说白了，它的痛点不是“做错事”，而是“做过了头”，把本来几分钟能收工的简单事情复杂化了。

---

## 2. 根因拆解：不全是 Astra 的锅，Codex 的默认提示词在“拱火”

为什么 Astra 这么喜欢自作主张？我去翻了 OpenAI 的 GPT-6 官方使用指南，里面明确提到：**Astra 本身比旧模型更倾向于停下来向用户提问**。单看模型底子，它其实并不算冒进。

真正的问题出在 **Codex CLI 的系统提示词**这一层。

在 Codex 发给模型的默认模式指令（[`default.md`](https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/default.md)）里，有这么一句关键指令：

> *In Default mode, strongly prefer making reasonable assumptions and executing the user's request rather than stopping to ask questions.*
> （在默认模式下，强烈建议自行做出合理假设并直接执行用户请求，而不是停下来提问。）

一个执行力本来就很强、习惯主动把事做完的模型，叠加上“别问，自己猜着往下做”的系统指令，化学反应就来了：Astra 会倾向于替你多想一步、举一反三，一个小改动说着说着就演变成了大工程。

虽然 Codex 内置提示词里也写了官方的测试校准原则（比如不要给可回滚、低风险的改动写多余测试），但官方提示词终究是通用原则，它并不知道你项目的真实背景和当前任务的轻重缓急。

所以，光靠官方默认提示词挡不住它发散，必须由我们在本地配置里把边界补上——而且**必须在开工前就写好**。道理很简单：做得少了，大不了让它再补一轮；但一旦做多了，多出来的代码你得手动清理，前面烧掉的 Token 也收不回来了。

## 3. `AGENTS.md` 别一刀切删光，要把踩过的边界写进去

Astra 发布后，社区里有不少文章建议“先把 `AGENTS.md` 删光”。OpenAI 官方博客也强烈建议大家审计现有的 `AGENTS.md` 和 Skills——因为 Astra 对指令极其敏感，以前为了哄旧模型干活而写的“每次必须先读某某文件”“每次改完必须跑全量测试”这类死板规则，确实该清理掉。

这一点我非常赞同：**旧模型时代的保姆式规则该删就删，Astra 自己能干好的事，留给它自由发挥。**

但“删旧规则”不等于“裸奔”。如果你只在 `AGENTS.md` 里写一句笼统的 `不要过度设计`，基本没有任何效果——因为落到具体代码上，模型根本不知道什么叫“过度”。

现在我的全局 `AGENTS.md` 只保留**可判断、可执行的边界规则**，核心就五条：

1. **先锁定范围再动手**：先从当前请求里提取预期结果、允许修改的对象、必须保持的约束和验收条件。如果路径不清楚，先做一次有边界的查找，只做最小充分改动。
2. **只读请求严禁动手**：解释、诊断、代码评审（Review）类请求，只做排查和报告。让你“看代码”，不代表授权你去跑测试、加探针或做完整审计。
3. **不扩展未要求的机制**：基于现有代码模式做够用的最小改动，不顺手新增兼容层、特性开关（Feature Flag）、新依赖或额外抽象。
4. **测试颗粒度跟着风险走**：可逆、低风险的改动，不写“把实现逻辑复述一遍”的测试；小 Demo 或单纯的版本更新，绝不引入新的测试框架或 CI 门禁；不写只校验版本号、文件数量、文案措辞的测试。
5. **达到验收就停**：顺手发现的其他问题，不等于获准当场修复。只要不阻塞当前验收，统一在交付报告里列出来，交给人来决定。

这五条属于通用底线，我放在全局 `~/.codex/AGENTS.md` 里，对所有项目生效。到了具体项目仓库，你还可以进一步补充项目级禁忌——比如“本项目严禁引入某某库”“优先复用某个现有工具函数”，这些项目特有的取舍，模型自己是猜不出来的。

## 4. 全局配置管“通则”，单次任务用“结构化契约”管范围

全局 `AGENTS.md` 解决的是通用行为准则，但它不知道你**这一次**任务具体要什么、不要什么。

OpenAI 的 Codex 最佳实践里专门提到一个常见误区：不要把长期规则塞进单次任务 Prompt，长期规则应该进 `AGENTS.md`。反过来也一样——**单次任务的边界，必须在每次派活时写清楚。**

我现在给 Astra 派活时，开头都会用固定的几行结构把框画好：
- **目标**
- **为什么做**（复杂任务强烈建议加上，帮模型判断“做到什么程度就够用”）
- **允许修改**
- **必须保持**
- **不在范围内**
- **验收标准**

有人把这种写法戏称为“GPT 八股文”。其实你完全不需要每次纯手写——可以在动手写代码前，先让 Codex 帮你把这几项确认清楚；遇到复杂任务，直接开启 `/plan` 模式，先跟它把方案细节聊透、落成文档，再让它开干。

## 5. 限制规则要精准，否则它会变成“事事请示的复读机”

防过度设计时，很容易踩进另一个反方向的坑：**限制词写得太重，导致 Codex 动不动就停下来请示你。**

前面说过，Astra 天生比旧模型更爱提问。如果你在规则里大量堆砌“先问我”“等我批准后再做”，跑长程任务时你会非常痛苦——它每改两行就停下来等你点确认。

解决办法是：**把“需要人确认的事”缩到最窄，同时明确告诉它在范围内拥有哪些自主权。**

OpenAI 官方文档里给过一个非常漂亮的正面示范：

> *The local tests use disposable fixtures and have no production access. Run them, fix failures caused by the requested change, and rerun affected tests without asking for approval at each step.*
> （本地测试使用的是一次性测试数据，且不会触碰生产环境。请直接运行测试、修复由本次改动引起的失败，并重跑受影响的测试，无需每一步都请求批准。）

你看，无论是“闷头乱加戏”还是“走一步问一步”，本质上都是因为**模型不清楚安全的边界在哪里**。把这个边界清晰地定义出来，恰恰是我们作为开发者的核心价值。

## 6. 想省 Token，别急着降级用便宜模型

当 Token 额度告急时，很多人的第一反应是：换个便宜点的小模型吧。说实话，我不太建议这么干。

Claude Code 负责人 Boris Cherny 年初分享过自己的习惯：所有任务一律用 Opus + Thinking。虽然 Opus 比 Sonnet 更贵也更慢，但它需要人工纠偏的次数少得多，工具调用也更准，算总账反而比小模型更快。

OpenAI 对 Astra 的定位也是一样的逻辑：虽然单价高于旧模型，但按“完成单个任务的综合成本”来算，反而更省。

如果为了省单价换成便宜模型，往往会遇到反方向的麻烦：听不懂复杂目标、偷懒糊弄、代码质量滑坡、同一条指令要反复强调，甚至还得专门装个“催促干活”的 Skill 才肯好好写代码。你省下来的那点单价，最后全贴在来回返工的轮次和时间上了。

**真正高效的省 Token 姿势，是用强模型 + 清晰的边界约束，争取一把做对、做完就停。** 如果平时高频用 Codex 跑任务、经常遇到额度不够用的情况，比起降级成小模型反复返工，更建议直接升级或续费高额度订阅（需要升级充值 ChatGPT Plus / Pro 的朋友可以直接用 [GetGPTPlus](https://getgptplus.app/) 自助搞定）。

## 7. 全局 `AGENTS.md` 与任务提示词模板

下面是我目前自用的完整配置。你可以直接将第一部分写入全局 `~/.codex/AGENTS.md`，并根据自己的技术栈微调。

### 7.1 全局配置模板（`~/.codex/AGENTS.md`）

```markdown
## 任务范围
从当前请求里找出目标、允许修改的对象、必须保持的约束和验收条件。路径不清楚时，先做一次有边界的查找。
按现有代码和模式做最小的充分改动，不新增兼容层、开关、依赖或抽象。

## 只读请求
解释、诊断、评审类请求只排查和报告，不改代码。静态检查不授权跑测试、探针或完整审计。

## 测试与验证
可逆、低风险的改动不写复述实现的测试。小 demo 或版本更新不加测试框架、检查器或 CI 门禁。
不写只验证版本号、文件数量、措辞、字段顺序的测试。
跑与改动相关的检查，通过后只在出现新改动、失败或具体风险时扩大验证。

## 自主与确认
范围内的读、改、测直接做。提交、推送、部署、写外部系统或明显扩大范围前，先做完能做的部分，再说明原因和最小扩展，等我确认。

## 交付
发现问题不等于获准修复。不阻塞验收的问题交付时列出。
文档归档只保留需要的文档、脚本和结果汇总。
达到验收就停，说明改了哪些文件、验证结果、没验证的部分。
```

### 7.2 单次任务 Prompt 模板

每次派发中大型或边界容易模糊的任务时，直接复制以下结构填空：

```markdown
目标：[预期行为]
为什么做：[要解决什么问题，做到什么程度就够]
允许修改：[文件或路径；只读任务写「只读」]
必须保持：[接口、默认行为、已确认的设计]
不在范围内：[最要紧的一两项]
验收：[可观察的结果和要跑的检查]
```
